# TUI 审计与优化建议（2026-10-28）

范围：`packages/oran-code/src/tui` 全部 33 个文件（约 7.5k 行），以及它的驱动通路
`session.ts` → `controller.ts` → `tui/renderer.ts` → `ink-app.tsx`，和 `session-store.ts` 的落盘路径。

方法：

- 逐文件阅读，并对着 Ink 5.2.1 的 `use-input.js` / `parse-keypress.js` 核对按键行为；
- 用仓库自带 `tsx` 直接 import 真实模块做微基准（Node 24.11，本机，Windows 11）。
  绝对毫秒数会随机器变化，但线性/二次的增长规律和相对排序是结构性的；
- 用真实 `InkTuiApp.transcriptRenderSections()` 复现了 Static 边界问题；
- 只做 `tsc -p tsconfig.typecheck.json --noEmit`（基线通过），未运行完整应用和测试套件。

---

## 0. 结论先行

1. **方向不需要推翻。**「已完成历史交给 Ink `<Static>` + 只保留活动尾部 + 字符串行管线 + 渲染屏障」
   是正确的架构，也符合 Ink 文档对 `Static` 的定义（只渲染新增项、忽略旧项变化）。问题集中在若干实现细节。
2. **真正的卡顿不是"每帧重建 transcript"。** 每消息渲染有缓存，600 条消息的暖帧只要 0.68 ms。
   实测的主要开销是：
   - `wrapDisplayText` 二次复杂度：审批弹窗渲染 64KB 单行内容 **6.9 s**；32KB 单行 thought **1.14 s**；
   - 覆盖层"先排版全部行、再裁剪"：200 个 provider **35.5 ms/帧**；
   - 终端 resize 触发全量冷渲染：300 条 assistant 消息 **175 ms**；
   - 折叠段每帧重新排版、不缓存：60 段 **3.55 ms/帧**；
   - 光标行每帧对每个 grapheme 调一次 `visibleWidth`：71 字符 **1.39 ms/键**；
   - `Intl.Segmenter` 每次 `graphemes()` 都新建：**约 10–14 µs/次**，乘进以上所有路径。
3. **两个内容正确性缺陷**（不是性能）：
   - 已提交到 Static 的折叠段，后续完成的工具行**永久不显示**（已用真实代码路径复现）；
   - 审批弹窗默认项是「Allow for this task」而 `y` 是「Allow once」；弹窗超高时选项和提示行被裁掉。
4. **隐藏大头是落盘 I/O**：每个非 delta 事件在 250ms 防抖后重写整个 sidecar（本机现存文件最大 422KB），
   任务结束还会连续写两次；`SessionStore.update()` 每次做 2–3 次深拷贝。
5. **渲染屏障给 agent loop 加了固定成本**：`assistant_end` 被映射为 `terminal`，每轮固定 `await 40ms`；
   `plan_complete` 在事件回调里同步 `await` 一次全量落盘。
6. **可删代码不多（约 90 行）**，真正值得做的是"合并重复实现"和"按需渲染"；
   删死代码改善的是可维护性，不会明显降开销——降开销靠第 1 节的几条。

### 0.1 已确认做得好、不建议改动的部分

- 每消息渲染缓存 + Markdown 稳定前缀缓存：暖帧 600 条消息 0.68 ms，说明缓存策略是有效的；
- `<Static>` 负责已封存历史、活动区只放尾部：符合 Ink 的语义，也是长会话不爆内存的正确做法；
- 渲染屏障的释放路径完整（提交回调 / destroy / rerender 抛错 / 1s 超时兜底）；
- bracketed paste + 鼠标序列在进入 Ink 之前剥离（含跨 chunk 缓冲与 40ms 透传兜底）；
- 主题支持 `NO_COLOR` / `ORAN_THEME` / `COLORFGBG`，mono 模式保留字重层级。

这些是本轮审计中**不应**被"优化"掉的设计。

## 1. 性能：实测热点（按影响排序）

### P1 `wrapDisplayText` 是二次复杂度（最高优先级）

`src/tui/text-width.ts:122-163`。注释写着"每行只 segment 一次"，但循环里每次都对**剩余整串**
重新 `graphemes(remaining)`，再 `slice().join().trimStart()`。一行需要 k 段就做 k 次全串分段。

实测（width=100，无空格长串）：

| 输入长度 | 耗时 |
|---|---|
| 2 000 字符 | 6.0 ms |
| 4 000 字符 | 18.2 ms |
| 8 000 字符 | 75.2 ms |

它是下面几条的公共放大器。触发点全部是真实 UI：

| 场景 | 实测 |
|---|---|
| `renderMessage(streaming thought, 8KB 单行)`（只显示 3 行预览） | **64.7 ms/帧** |
| `renderMessage(streaming thought, 32KB 单行)` | **1 143 ms/帧** |
| `approvalDialogLines(write_file, 64KB 单行)` | **6 929 ms** |
| `approvalDialogLines(write_file, 160KB/8000 行)` | 307 ms/帧 |
| `renderToolMessage(run_command, 128KB 单行)` | 0.15 ms（有 `width*2` 截断，安全） |

原因链：`message-renderer.ts:158-162` 的 `thoughtPreviewLines` 为了取 3 行，把整个 body 先完整
wrap 一遍；`approval-dialog.ts:19-25` 把 `write_file` 的 `content` 参数原样当一行渲染。

**修法**：`wrapDisplayText` 先 `graphemes` 一次，然后用下标走 `symbols` 构建每段（保留现有的
`lastSpace` 断词规则和"单符号超宽"分支）；给 `thoughtPreviewLines` / 审批弹窗一个"只产出前 N 行"的
上限版本；审批弹窗对超长参数值按行数/字符数截断并注明"省略 N 行"。

**风险**：输出必须逐字节不变（第 3 行替换为 `…` 的条件、断词位置）。

### P2 覆盖层整表排版后再裁剪

`render.tsx:189-209` 的 `fitOverlayLines` 在**所有行都排版完之后**才切片。除命令面板
（`command-palette.ts:42` 先 `visibleSelection` 再排版）外，sessions / files / follow-ups /
providers / models / connect 都是先格式化全部行：

- `providersListLines(200 行)` 实测 **35.5 ms/帧**；
- 每按一次 ↑↓ 都重算一遍，而实际只显示 `overlayCapacity`（约 10）行；
- `command-palette.ts:44-46` 也仍然对全部候选算 `nameWidth`，再切 7 行。

**修法**：各列表渲染器接受 `height`（或 `window`），先 `visibleSelection` 再逐行格式化；
宽度只按可见窗口 + 选中行计算。

### P3 冷渲染（resize）与"已提交前缀"的重复工作

`ink-app.tsx:1180-1210`：

1. `linesWithAnchors` 渲染**全部**消息（缓存命中时便宜，但 resize 改宽度会让所有缓存失效）；
2. `groupedLines` 对**全部行**建 Map，而只有 `staticMessages` 会用到；
3. 最后又 `filter` 掉已提交的行——已提交行的渲染结果**被丢弃**。

实测：

- 暖缓存 `renderLines(600 msgs)` = 0.68 ms（说明缓存是有效的，这条不是每帧大头）；
- **冷渲染** 300 条 assistant 消息 = **175 ms**；混合 600 条 = 75 ms；
- `groupedLines` 对 4 412 行建 Map = 0.19 ms，`liveLines` filter = 0.07 ms。

**修法**：维护"已提交到 Static 的边界"，只渲染边界之后的部分；已提交消息在提交时渲染一次后
**从 `TranscriptView` 缓存里驱逐**（它的文本已经在 `committedStaticTranscriptItems` 里）。
resize 时也就只重排活动区，而不是全部历史。

**风险（必须处理）**：折叠段以 `messages[0].id` 作为行归属（`transcript-view.ts:72`），
一个段可能跨过边界；边界必须取在**段**粒度上，滚动锚点（`findAnchoredLine`）也要按切片起点偏移。

### P4 折叠段从不走缓存，每帧重排

`transcript-view.ts:68-84`：`segment` 分支直接调 `renderCollapsedSegment`，不查也不写 `this.cache`；
而它只依赖 `(thoughtCount, toolCount, thoughtDurationMs, width)`。实测 **约 59 µs/段**，
60 段 = **3.55 ms/帧**（同消息全缓存时 0.45 ms vs 4.01 ms）。

**修法**：用同一张 Map 缓存，key 含段 id + `toolCount|thoughtCount|thoughtDurationMs|width`；
`pruneCache` 的活跃 id 集合要包含段 id；`expandedToolGroupIds` 命中的展开形态不能和折叠形态共用槽位。

### P5 光标行对每个 grapheme 调 `visibleWidth`

`render.tsx:289-300`：`symbols` 已经切好，却又对**单个** grapheme 调 `visibleWidth`，
后者再次 `stripTerminalMarkup` + `graphemes`（还新建 Segmenter）。实测 **1.39 ms**（71 字符，光标在行尾）。

**修法**：改成 `graphemeWidth(symbol)`——`visibleWidth` 内部 reduce 用的就是它，对已切好的单 grapheme 等价。

### P6 `Intl.Segmenter` 每次 `graphemes()` 都新建

`text-width.ts:7-22`。实测新建 + 分段 "a" = 16.7 µs，复用 = 3.3 µs，**约 13 µs 是纯构造**。
`graphemes(72 字符)` 31 µs，`visibleWidth` 28 µs。它出现在每一条文本路径上（footer、markdown、
composer、截断、换行）。

**修法**：模块级懒建一个 Segmenter；再加一条 ASCII 快路径（`/^[\x20-\x7e\n\t]*$/` 时
width = 字符数、graphemes = 字符数组）。ASCII 快路径能把 P5 从 1.39 ms 降到近似 0，
把 footer 从 0.11 ms 降到 0.01 ms。

### P7 每帧重复计算 composer 视觉行

`ink-app.tsx:1413-1414` 先 `visualLines(...)`，再 `cursorVisualPosition(...)`，而后者内部**又**
算一遍 `visualLines`（`composer.ts:256-265`）；`canMoveComposerVertically`（`ink-app.tsx:959-964`）
再把两者都算一遍，随后 `moveCursor(..., width)` 内部**再**各算一遍（`composer.ts:231-232`）。
按一次 ↑/↓ = 4 次完整换行计算。实测单行 71 字符 `visualLines` 0.175 ms + `cursorVisualPosition`
0.187 ms；长行/中文按倍数增长。

**修法**：提供 `cursorVisualPositionFor(lines, composer)`，每帧只算一次并向下传；
上下移动复用同一份结果。必须保留现有 `startColumn` 行/列算法（IME 停靠依赖它）。

### P8 每帧把整份 transcript 物化 + 每帧扫全表

- `transcriptRenderSections` 每帧对全部行 `flatMap` 出 `{text, messageId, lineOffset}` 对象（约 0.9 ms @4.4k 行）；
- 滚轮处理里 `scrollTranscriptBy` → `liveTranscriptLines()`（`ink-app.tsx:1122-1126,1169`）
  **再**渲染一遍全表，随后 `invalidate()` 的帧还会再来一次；
- `staticTranscriptCount` 每帧从 0 扫（实测仅 0.017 ms，成本低，但可以缓存）；
- `isSessionBusy` 每帧被调用 4 次（`ink-app.tsx:1385`、`footer.ts:60/163`、`status-indicator.ts:140`）；
  `workingLabel` 里还有 `[...transcript].reverse()` 的整表拷贝（`status-indicator.ts:182-184`）。

实测这些单次都只有 0.005–0.02 ms 量级，**不是主要瓶颈**；建议随 P3 一起收敛成一次"活动状态"计算，
不单独排期。

### P9 每轮 assistant 都被 spinner tick 判脏

`transcript-view.ts:261-266`：assistant streaming 时把 `liveTick` 放进缓存 signature，但 assistant
渲染根本不用 tick。结果是每 120ms 及每次按键都重排一遍流式 assistant（约 0.13 ms/帧，长段落更多）。

**修法**：`liveSignature` 对 assistant 返回 0；thought/tool 才需要 tick。

### P10 次要项（实测很小，顺手清理即可）

- 每帧 `isSessionBusy` 的 4 次全表扫描、`workSummaryLine` 的全表 filter（合计 <0.05 ms）；
- `useInput((input,key)=>app.handleKey(...))`（`ink-app.tsx:1405`）每次渲染都是新闭包，
  Ink 的 effect 依赖 `inputHandler`，等于每帧摘挂一次 stdin 监听（未测，推测 µs 级）；
- `message-reducer.ts:102` 每个 delta 对累计全文 `includes("PLAN_COMPLETE")`；
- `session-debug.ts:41-67` 每个 delta 都 `JSON.stringify` 一次，然后才在 sink 里检查 `ORAN_DEBUG`；
- `ink-app.tsx:1001-1006` 的 `onRenderDebug` 也是先 stringify 再被 sink 丢弃。

## 2. 落盘与渲染屏障（TUI 之外，但直接决定交互手感）

### I/O：每个非 delta 事件重写整份 sidecar

- `session.ts:1461` 对每个非 delta 事件调 `scheduleTuiSessionPersist()`，250ms 防抖后
  `persistTuiSession(false)`；
- 注释说"只写元数据"，但 `persistTuiSession` 始终传 `conversation`（`session.ts:1359-1398`），
  而 `SessionStore.update()` 每次：
  - `cloneSession(existing)` + `cloneMessages(conversation)` + 返回前 `cloneSession(next)`；
  - `writeSidecar()` 里 `JSON.stringify(stateSnapshotRecord(next))`，**包含整个 `messages` 与 `history`**
    （`session-store.ts:839-846,460-472`）。
- 本机 `~/.oran/sessions` 里现存最大 sidecar **422 KB**，另一个 259 KB——也就是说一次"元数据更新"
  会重写几百 KB。
- 任务结束连写两次同一内容：`startTask` finally 的 `await persistTuiSession()`（`session.ts:927`）
  和 `launchTask` finally 的 `void persistTuiSession()`（`session.ts:970`）。
- `session-crud.ts:60/105/164` 在打开会话列表、删除、重命名前先落盘，纯属多余。

**建议**：任务结束二选一；`update()` 在 patch 不含 messages/history 时按引用共享并只写小型 meta sidecar；
打开/删除/重命名前不写；250ms 防抖只写增量记录。

### 屏障：每轮固定 40ms + 事件回调里同步落盘

- `ink-app.tsx:1039-1041`：`terminal` 提交类型固定 `await setTimeout(40)`；
  `session.ts:2289-2313` 把 `assistant_end` 映射成 `terminal` → **每个模型回合多 40ms**，10 轮 = 400ms；
  `error`/`cancelled` 也要睡，尽管后面没有事件了。
  屏障本身的释放路径是完整的（提交回调 / destroy / rerender 抛错 / 1s 超时兜底），这点做得对。
- `session.ts:1437-1452`：`plan_complete` 在事件回调里先 `refreshTui()` 再 `await persistTuiSession()`，
  计划完成的画面要等一次全量落盘才出现。
- `approval_request` 先发事件（绘制一帧无弹窗）再 `openApproval` 里 `invalidate()`（第二帧）。

**建议**：40ms 改成"等提交即返回"或直接去掉（先确认不是为了 IME/粘贴时序）；
`plan_complete` 的落盘改成调度；弹窗在 `approval_request` 处理时直接写入 overlay。

### `refreshContext` 让 token 估算的 memo 永远失效

`session.ts:1980` 每次 `estimateTokens(this.conversation, [])` 都传**新的 `[]` 字面量**，
`context/manager.ts:167-186` 的 memo 比较 `memo.tools === tools` → 永不命中，还顺手把 memo 覆盖成
`tools: []`。`estimatedRequestTokens` 内部是 `JSON.stringify(整个会话)` + 全串正则。
实测 200 条消息 **2.58 ms**、800 条 **3.21 ms**，而 `refreshTui` 每轮要调多次。

**建议**：把 `[]` 提成模块常量（或加一个不收 tools 的重载）；按 revision 缓存估算值。

## 3. 正确性与结构缺陷

### C1（已复现）Static 边界之后完成的工具行永久消失

场景：一个 thought + 2 个只读工具完成 → 折叠成 `◇ 2 tools` 并提交到 Static；
随后同批第 3 个工具完成 → 它成为同一个折叠段的成员，但段行全部归到 `messages[0].id`，
该 id 已在 `committedStaticTranscriptIds` 里 → 新行既不出现在 Static（不能改已渲染项），
也不出现在 live 区（被 filter 掉）。

用真实 `InkTuiApp.transcriptRenderSections()` 复现：

```
static items: [ 'message-1' ]        // "◇ 2 tools · ctrl+t: latest details"
AFTER THIRD TOOL
static items: [ 'message-1' ]
live lines: (空)
contains '3 tools': false
contains f3.ts: false
```

这是 Ink `<Static>` 的语义决定的（readme：只渲染新项，旧项变化被忽略），所以修法必须在提交侧：

- 一个"仍在增长的段"不要提交（把最后一段一直留在活动区），或
- 段行按"最后一个成员 id"归属并在增长时重新提交一个**新 item**（新 id），或
- 提交时把段视为不可变边界：后续工具另起一行渲染。

同时注意这与 P3 的裁剪互相依赖：裁剪边界必须按段取整。

### C2（已复现）审批弹窗的默认项 ≠ `y`，溢出时选项和提示被裁掉

- `approval-dialog.ts:7` 选项顺序是 `[Allow for this task, Allow once, Always allow, Reject]`，
  `ink-app.tsx:858` 把光标放在 0 → **回车默认授予"本任务内全部允许"**；
  而 `interaction.ts:19` 的 `y` 映射到索引 1（Allow once）。提示行同时写着两者，看不出差异。
- `fitOverlayLines`（`render.tsx:199-208`）假设"前两行是头部"，而审批弹窗第 2 行是空行；
  当详情比窗口长时，它把**选中行钉在最后一行**，四个选项和提示行全部被裁掉。实测（100 列）：

```
--- capacity 10 -> 10 lines
Permission required

line 54 … line 59

{inverse}  Allow for this task{/inverse}
```

而 `write_file` 的 `content` 会让详情远超窗口——见 P1 的 6.9 s 同一路径。

**建议**：默认项改成 `Allow once`（或把 `Allow for this task` 移到 `y` 的位置）；
选项区固定占据底部窗口，详情区分页；为所有覆盖层预留尾部提示行。

### C3 Esc 取消提示永远不显示

`ink-app.tsx:410` 写 `status = "press Esc again to cancel"`，但 `footer.ts:162-173` 的
`explicitStatus` 在 `isSessionBusy` 时直接返回 `undefined`；而 Esc 分支只在忙碌时可进入。
所以第一次 Esc 没有任何反馈，第二次才突然取消。`"cancelling..."` 同理。
（对比：`"press Ctrl+C again to exit"` 能显示，因为那时空闲。）

**建议**：把这类提示放到忙碌态的专用通道——working line（`workingIndicatorLine`）里追加
`· again to cancel`，或给 `explicitStatus` 一个小白名单。

### C4 物理 Home/End 无效；物理 Delete 退化为退格

已在 Ink 5.2.1 源码确认：`parse-keypress` 把 `ESC[3~` 解析成 `name: 'delete'`、`ESC[H`/`ESC[F`
解析成 `home`/`end`；`use-input.js:68-70` 对 `nonAlphanumericKeys`（含 delete/home/end/backspace）
把 `input` 置空。于是：

- `isDeleteForward`（`keys.ts:30-37`）里 `input === "\x1b[3~"` 等分支**永远不可达**；
  Backspace 和 Delete 都是 `key.delete`，先命中 `isDeleteBackward` → **Delete 键永远向后删**；
- `isHomeKey`/`isEndKey`（`keys.ts:14-22`）里所有转义序列分支不可达，物理 Home/End 无效
  （只有 Ctrl+A / Ctrl+E 有效）。而 `shortcuts.ts:22` 明确写着"Home/End 到当前行首尾"。

`tests/tui-keys.test.ts` 直接用原始转义串调用谓词，所以测得过——但真实输入路径永远不会产生那种串。

**建议**：要么在输入 Transform 层（`terminal-streams.ts`）把 `ESC[3~`/`ESC[H`/`ESC[F` 映射成
带内标记后交给 `handleKey`（那里还能拿到原始字节），要么承认只支持向后删并删掉 `isDeleteForward`
与那条测试，同时修正快捷键表。

### C5 旧工具/思考的完整内容不可达 + `expandedToolGroupIds` 是死状态

- `expanded` 只在 `openLatestActivityDetails`（`ink-app.tsx:1230`）里对副本置 true；
  工具行永远以 8 头 + 4 尾（失败 2 行）呈现。
- `state.expandedToolGroupIds` 在 `src` 里**只有 clear / 读**，从不 `add`（只有测试会 add）。
  所以"展开的段"这条渲染分支只在 details 覆盖层里靠临时 Set 用到。
- 结论：一段历史之后，用户**无法再查看任何旧工具的输出正文**（终端回滚里也只有截断后的文本）。

**建议**：要么删掉 `expandedToolGroupIds` 和对应分支（承认 details 只服务最近一段），
要么补一个"选择某一行打开详情"的入口（例如 `/details N` 或方向键在活动区选中行）。

### C6 恢复会话可能永久 busy

`session-store.ts:1092-1102` 会保留 `streaming: true` / `status: "running"`；`restoreSession`
（`ink-app.tsx:712-748`）只重置顶层标志，不清消息级标志。`isSessionBusy` 读 transcript →
一个残留行就让 spinner 永远转、状态栏永远被抑制、`staticTranscriptCount` 冻结。
进程在 `assistant_start` 落盘之后崩溃即可触发。

**建议**：加载/恢复时归一化：`streaming=false`；`tool.status==="running"` → `cancelled`/`failure` + 摘要。

### C7 提交成功后清空全部 `pastes`，会吃掉提交期间的新粘贴

`ink-app.tsx:783-797`：`submitBusy` 只挡第二次提交，不挡输入。`await onInput` 期间用户再粘贴，
`registerPaste` 追加到 `composer.pastes`；成功后 `this.state.composer.pastes = []` 把新的也清掉，
新草稿里的 `[paste #N …]` 再也无法展开，会按字面发给模型。

**建议**：记录本次提交用到的 paste 条数，成功后只移除这些（或按草稿 generation 判断）。

### C8 输入流的生命周期细节

`terminal-streams.ts`：

- `:198-204` 的 1s 粘贴兜底计时器没有 `unref()`（鼠标计时器有），退出时最多拖住进程 1s，
  且可能在流已废弃后 `push`；
- `flush()`（`:224-232`）放出了 `mousePrefix`，但**静默丢弃**未完成的 `pasteBuffer`；
- `:150-180` 进入粘贴帧时没有清掉挂起的 `mousePrefix`，跨 chunk 可能漏判粘贴起点；
- 超时把 `inPaste` 置 false 后，迟到的 `ESC[201~` 会作为普通文本进入 Ink。

### C9 其他值得记录的小问题

- `setComposerValue`（`state.ts:121-128`）只处理 `\r\n`，不处理孤立 `\r`（`insertText` 处理了）。
- `deleteBackward`/`deleteForward`/`deleteWordBackward` 在"什么都不会删"时也先压 undo 栈，
  会清空 redo（`composer.ts:131-135,167-169,186-188`）。
- `interaction.ts` 的 `import` 出现在文件中部（规范问题）。
- `message-reducer.ts:102` 每个 delta `includes` 全串；`processedSequences` 每个事件留一个字符串
  （整个 task 不清），`retiredTaskIds` 进程内只增不减。
- `toolCallKey` 用 `name:createdAt`（毫秒）作 fallback，同毫秒同名并发调用会合并成一行。

## 5. 界面优化建议（按价值排序）

### U1 审批弹窗：默认项、布局、可读性（最高）

见 C2。另外：把「这个操作会改哪些文件 / 执行什么命令」放在第一屏，`content`/`diff` 这类大参数
只显示摘要（`+N lines`、首尾几行）。审批是安全关键路径，弹窗的默认值和可视性都应按"保守"设计。

### U2 忙碌态只有一条通道，提示应集中

- Esc 取消确认（C3）应该出现在 working line；
- 现在同一件事重复三次：working line 的 `[1 background job: npm run dev] 12s`
  （`status-indicator.ts:124`）、footer 的 `1 job running`（`footer.ts:36-37`）、
  子代理面板（`status-indicator.ts:74`）与 footer 的 `2 subagents running (+1 queued)`。
  面板可见时，footer 的这两枚徽标可以撤掉。

### U3 footer 信息层级

当前第 2 行是
`[usage] · follow-ups · perm:mode · ctx NN% · subagents · jobs · status` 全用 ` · ` 连接，
而 `usage` 内部又是 ` · `（`footer.ts:112-118`）。建议：

- usage 整体加括号（`[in 12.3k · out 1.2k · cache 65%]`），和其余徽标形成两级；
- 状态（错误、`draft cleared`）优先显示——现在是右截断（`footer.ts:53`），最先被砍；
- `tok/s` 同时在 footer 和完成摘要（`footer.ts:80`）出现，留一处。

### U4 列表类覆盖层的一致性与可达性

- 提示语三种：`Up/Down Select · Tab Complete · Enter Run · Esc Close`（命令面板）、
  `↑↓ Select   Enter Confirm…`（审批）、`↑↓ Navigate…`（提问）。统一成 `↑↓`；
- sessions/files/follow-ups/providers 的提示**都没写 ↑↓**，但键是有效的；
- 只有命令面板有 `3/120` 位置指示；其余列表被窗口化却没有位置感；
- 确认类弹窗（`Enter Confirm   Esc Cancel`）没写 ←→ 也能切换按钮；
- `providers-list.ts:11,28` 用裸 `─`，其余覆盖层用 `dimHorizontalRule`——亮度不一致。

### U5 子代理面板

- `TASK_PANEL_MAX_ROWS = 6` 不随终端高度变化；24 行终端里 6 个子代理会占掉一半 chrome。
  建议 `min(6, max(2, floor(rows/4)))`；
- 失败行只有 `✗ role · name · failed 12.0s`，不显示 `task.error`（`/tasks` 里显示了）；
- 60s 后已结束任务直接消失，没有任何可回看入口；`/tasks` 的提示只在溢出行的文案里。

### U6 composer 在模态覆盖层下仍在"邀请输入"

`composerPrefix` 对模态层画 `! `（`render.tsx:252`），composer 文本和光标仍渲染，
真实光标也仍会停靠（`parkComposerCursor` 只跳过了 approval/question，`ink-app.tsx:1513`）——
但按键全部被覆盖层吞掉。建议：模态层显示 `sessions> ` 之类的前缀，并跳过光标停靠。

### U7 `/model` 覆盖层是死路

`render.tsx:70-75` 只有标题、横线、列表：没有提示行、没有空列表文案；

`loadModels` 失败时是一个空白面板，且加载期间没有任何反馈。

### U8 完成摘要行永远用成功色

`ink-app.tsx:1565` 对 `workSummaryLine` 固定用 `COLORS.success`，而它会产出 `× Failed` /

### U9 欢迎卡与语言

- `welcomeModelLabel` 把 provider 前缀切掉（`render.tsx:51-53`），卡片显示 `gpt-5 high`，

### U12 状态残留

`openFollowUps` 把 `N follow-up(s) queued` 写进 `session.status`（`overlay-handlers.ts:198`），

## 6. 建议的落地顺序

按"低风险 → 高收益"分批，每批都可单独提交、单独验证（`pnpm typecheck` + 针对性微基准，
不跑全量测试）。

**Batch 1：纯性能，不改任何可见输出**
1. `wrapDisplayText` 单次分段 + 输出行上限（P1）；`thoughtPreviewLines` 走上限版本；
   审批弹窗对大参数值截断。
2. `Intl.Segmenter` 提到模块级 + ASCII 快路径（P6）。
3. 光标行 `visibleWidth` → `graphemeWidth`（P5）。
4. 折叠段缓存（P4）。
5. assistant 的 `liveSignature` 返回 0（P9）。
6. `visualLines`/`cursorVisualPosition` 每帧只算一次（P7）。
验证：微基准对比（审批弹窗 64KB、32KB thought、60 段帧、71 字符光标行、200 行 provider 列表）；
`tsc` 通过；现有 TUI 渲染测试通过。

**Batch 2：交互正确性（用户可见，但改动集中）**
1. Static 边界：不再丢工具行（C1），并与 P3 的"只渲染活动尾部"一起设计。
2. 审批默认项与选项区布局（C2 + U1）。
3. Esc 取消提示进 working line（C3）。
4. Home/End/Delete 键（C4）——先确认产品上要支持哪个。
5. 恢复会话归一化（C6）、提交期间粘贴（C7）。

**Batch 3：界面一致性（无行为变更，只有文案/布局/颜色）**
U3–U10 的小项：提示语统一、位置指示、footer 分组、完成摘要配色、provider/model 行宽、
`/model` 加载与错误态、子代理面板高度与失败原因。

**Batch 4：结构与 I/O（收益大、面也大）**
1. 落盘：去掉重复写、meta-only sidecar（第 2 节）。
2. 屏障：去掉/缩短 40ms，`plan_complete` 不再同步落盘。
3. `refreshContext` 的 token 估算 memo。
4. `id → message` / `callKey → message` 索引（为 P3/P8 与 reducer 的 O(n) 查找铺路）。
5. `{inverse}` → 结构化 `OverlayLine`；合并三套选择移动、两套删除确认、四种 open* 覆盖层。

**Batch 5（可选）：删除 4.1 的死代码并去掉多余 export。**
放在最后，避免和前面的重构互相制造冲突。
