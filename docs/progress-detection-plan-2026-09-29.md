# 无进展检测：功能改造规划（2026-09-29）

> 来源：模拟面试中反复被问到的两个场景（「每次读不同文件但一直在读」、「一轮任务确实要读很多文件会不会误伤」）→ 对 Codex / Claude Code / Qwen Code / Gemini CLI 的实现与事故报告做横向比对
> 目的：把「无进展检测」从**请求重复性判据**升级为**产出判据**，并解决「不误伤合法探索」这个反向问题
> 基线：`main` 分支，**22 个已注册工具 / 首轮暴露 19 / 首轮 Schema 12,557 字节**（2026-09-29 实测）；`src/loop.ts:5-6` 现有 `NoProgressReason = repeated_execution | repeated_error | semantic_stall`、`NoProgressStage = warning | reflection | pause`
> 状态：**纯设计文档，未落代码**。与 `docs/code-impact-graph-plan-2026-09-29.md` 互补：那份补「代码结构理解」，这份补「执行过程控制」，两者共用同一个 `.oran/` 状态目录。

## 一、要解决的问题

### 1.1 两个方向相反的失败

| #   | 场景                                     | 性质     | 现在的表现                                                                       |
| --- | ---------------------------------------- | -------- | -------------------------------------------------------------------------------- |
| 1   | **每次读的文件、内容都不同，但一直在读** | **漏检** | 所有判据失效——现有三类 reason 全部基于「重复」，对这种永不重复的模式一条都抓不到 |

这两个问题互相拉扯，**不能分别调参数**：把只读也纳入拦截 → 问题 2 发作；把只读完全放开 → 问题 1 抓不到。必须换机制。

## 二、对标证据

### 2.1 行业收敛出的检查顺序

所有严肃实现都装同一样东西：

```
迭代次数上限 → 进展检测 → 预算上限 → 验证器判定
```

**关键在「验证器判定」这一环**，各家做法一致：**不由模型自己判定是否完成**。

- Claude Code `/goal`（v2.1.139，2026-05-11 上线）：把 maker/checker 烤进停止条件——**Stop hook 里由一个小模型评估器判定 NO / YES**，评估者与工作者是两个模型、两套视角
- 铁律表述：**模型可以提出「完成」，但不能批准自己的「完成」**
- LoopX 的框架：把循环从模型的提示词与聊天历史里**抽出来，放进一个与 Agent 运行时无关的持久控制面**

### 2.2 它们踩过的坑（这一节是本规划的主要论据）

**Codex Desktop 的真实事故**（官方社区 bug 报告）：

> `Goal auto-continuation loop: 3,994 "remain paused" replies over 5.5 hours`

- 触发点：**一次上下文压缩之后，assistant 把任务重新当成「已暂停」**，然后 Goal 反复发起新 turn，assistant 反复回答「仍然暂停」
- **持续 5.5 小时、3994 次回复，直到人工介入**

同期另一条：`Codex Desktop repeatedly loses the original acceptance goal after compaction and enters endless subagent/test loops`。

**根因不是「检测不够灵敏」，是「目标在上下文压缩时被丢掉了」。** 这直接推出本设计的第 0 条约束：**进展状态必须存在会话之外。**

**反面教材 — Gemini CLI**（源码分析）：卡死判定依赖超时而非检测，**静默退出，没有独立的告警或恢复路径**，上层只看到「批次返回不完整」。教训：**要显式状态 + 恢复路径，不要静默退出。**

**Qwen Code 的一个真实 PR**（#5036）：

> `loop 检测触发后真的硬停掉重复的同一个 tool call，别让 agent 还在那反复执行卡死的动作。`

说明「检测触发了但没真的停」是被真实修过的缺陷类型。

### 2.3 判据来源

| 判据                         | 出处                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 迭代次数上限                 | 三家都有                                                                                                   |
| 调用/结果重复                | Qwen Code #5036                                                                                            |
| **成本增长而完成度不变**     | JetBrains：把 token 与调用量上涨**当作检测信号**，不只是账单问题                                           |
| **原始目标是否还在**         | Codex 事故（压缩后目标丢失）                                                                               |
| **测试数量没有减少**         | Anthropic harness 原文规则：`It is unacceptable to remove or edit tests`（防「删掉失败的测试让 CI 变绿」） |
| 证据须「新鲜」并绑定源码版本 | Proof-of-done 契约 + Proof-or-Stop 论文（证据门控生命周期）                                                |
| 终止态枚举                   | `verified / review-required / blocked / stopped-by-budget`                                                 |
| 轨迹级「坏循环」检测         | 论文 `Cycle Detection in Agentic Applications`（2025），专研「重复调用工具但无进展」                       |

### 2.4 一条必须记住的反面证据：独立验证的价值在「外部信号」

| 做法                             | 结果                                 |
| -------------------------------- | ------------------------------------ |
| GPT-4 **无外部反馈**自我审查修正 | **准确率反而下降**——改错的比改对的多 |
| 用搜索引擎 / 解释器验证          | 显著提升                             |
| 移除工具验证、只留自我评估       | 大部分提升消失                       |

**推论**：验证器要拿的是**测试结果、编译结果**这类生成时不存在的外部信号，不是「换个模型再看一遍代码」。

### 2.5 成本护栏的现实注脚

Uber 在四个月内烧完全年 AI 预算后，把工程师的 agent 工具费用上限压到每人每月 1500 美元。**预算护栏不是杞人忧天，是已经有人交过学费。**

## 三、抄什么、不抄什么

| #   | 设计点                | 对标做法                        | 我们的选择                                                                                 | 理由                                                                                        |
| --- | --------------------- | ------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 1   | 验证者是否独立        | Stop hook 里另一个模型判定      | **暂不做**（列为选做）                                                                     | 需要接外部证据（跑测试）与第二个模型预算；本项目已有双 Provider 适配层，接入成本低但排在 P2 |
| 2   | 状态存哪              | LoopX：独立于运行时的持久控制面 | **落 `.oran/` 状态目录**，与 `subagent/state-store.ts` 同策略（终态立即落盘 + 中间态防抖） | 复用已有落盘机制；不引入新基础设施                                                          |
| 3   | 干预强度              | 命中即停                        | **四档分级**：`info` / `signal` / `reflection` / `pause`                                   | 见 §5 取舍 2；低档只注入，不改行为                                                          |
| 4   | 判据数量              | 各家不一                        | **12 条，其中只有 6 条能停机**                                                             | 判据可以多，能停机的必须少——这是「不束手束脚」的结构性答案                                  |
| 5   | 成本增长              | JetBrains：当检测信号           | **采纳，但封顶 `reflection`**                                                              | 它是「看起来没推进」，不是「确定走不通」                                                    |
| 6   | 测试数减少 / 测试回退 | 布尔判定                        | **直接采纳，作硬证据**                                                                     | 可机械验证，且能抓「修好 A 弄坏 B」与作弊                                                   |
| 7   | 语义相似度判停滞      | 无成熟实现采用                  | **不做**                                                                                   | 不可验证、误判率无法量化；改用外部证据                                                      |
| 8   | 文件监听 / daemon     | 部分实现有                      | **不做**                                                                                   | 无异步窗口需求，净增复杂度                                                                  |

## 四、设计

### 4.1 三层结构

```
采集层（每轮结束） → 判定层（算出信号） → 门禁层（决定动作）
     只记录              只分类            少数信号能进
```

**判定层产出的是一个「信号列表」，不是「要不要停」的决定。** 这样绝大多数判据可以只记录、不动作。

### 4.2 数据模型

```ts
type TurnSnapshot = {
  turn: number;
  ts: string;
  // 任务级（只存一份）
  goalFingerprint: string; // 初始任务描述 + 验收标准的哈希
  allowedPaths: string[]; // 允许改动的文件集合
  // 每轮
  workspaceDigest: string; // 被跟踪文件内容哈希的集合
  toolCalls: Array<{
    name: string;
    argsDigest: string; // 归一化后的参数哈希
    resultDigest: string;
    ok: boolean;
    readonly: boolean; // 只读工具？
    mutated: boolean; // 真的改了吗（no-op 写入 = false）★
  }>;
  tokensIn: number;
  tokensOut: number;
  cost: number;
  // 外部证据（「可验证进度」的来源）
  evidence: {
    // ★
    testsPassed?: number;
    testsTotal?: number;
    typecheckOk?: boolean;
    buildOk?: boolean;
  };
};

type Phase = "explore" | "implement"; // ★ 核心状态

type ExplorationState = {
  phase: Phase;
  readonlyFilesRead: number; // 探索预算按「读取的文件数」计量，不是轮数
  exploreBudget: number; // f(任务规模) × 3~5
  implementTurns: number;
  implementBudget: number; // f(任务规模)
  knownSymbols: Set<string>; // 已读到的符号，用于算新颖度
  symbolSource: "graph" | "regex"; // ★ 符号来源分层（见 §4.6）；两条路径的 novelty 不可比
  noveltyEMA: number;
  lastRehearsal?: {
    // 上次结构化复述
    turn: number;
    hypothesis: string;
    excluded: string[];
    candidateSet: string[];
    nextCheck: string;
  };
  egressCount: number; // implement → explore 回退次数
};

type ProgressSignal = {
  kind:
    | "readonly_repeat"
    | "state_loop"
    | "low_symbol_novelty"
    | "write_repeat"
    | "cost_without_progress"
    | "phase_egress"
    | "same_error"
    | "goal_drift"
    | "test_regression"
    | "test_count_drop"
    | "implement_budget"
    | "rehearsal_diverged";
  severity: "info" | "warn" | "hard";
  detail: string;
  sinceTurn: number;
};
```

**三个字段是修 bug 与解题的关键**：`readonly` / `mutated` 分离（修 §1.2-c 的清零 bug）、`evidence`（唯一能判真进展的硬信号）、`phase`（分期）。

### 4.3 模块划分

| 文件                        | 职责                                                      |
| --------------------------- | --------------------------------------------------------- |
| `src/progress/capture.ts`   | 每轮快照采集：工具调用分类、工作区指纹、证据提取          |
| `src/progress/phase.ts`     | 探索/实现分期状态机、两套预算换算                         |
| `src/progress/signals.ts`   | 12 条判据计算，产出 `ProgressSignal[]`                    |
| `src/progress/rehearsal.ts` | 结构化复述的请求、解析、收敛判定                          |
| `src/progress/store.ts`     | 状态外置（照 `subagent/state-store.ts` 的落盘策略）       |
| `src/loop.ts`               | 改为调用上述模块；**`warning` / `reflection` 降为纯注入** |

### 4.4 判据总表（12 条，按准入分层）

| #   | 判据                                   | 判定方式        | 最高档               |
| --- | -------------------------------------- | --------------- | -------------------- |
| 1   | 只读重复                               | 计数            | `info`（**永不拦**） |
| 2   | 状态回环（`workspaceDigest` 回到旧值） | 布尔            | `signal`             |
| 3   | 符号新颖度过低                         | 比例 + EMA      | `signal`             |
| 4   | 写操作重复（归一化后）                 | 计数            | `reflection`         |
| 5   | 成本增长无进展                         | 比例            | `reflection`         |
| 6   | implement → explore 回退               | 计数            | `reflection`         |
| 7   | **同一错误连续 3 次**                  | 布尔 + 计数     | ✅ `pause`           |
| 8   | **目标漂移**（改动出 `allowedPaths`）  | 布尔 + 连续计数 | ✅ `pause`           |
| 9   | **测试回退**（`testsPassed` 下降）     | 布尔            | ✅ `pause`           |
| 10  | **测试数减少**（`testsTotal` 下降）    | 布尔            | ✅ `pause`           |
| 11  | **实现期轮次预算耗尽**                 | 按规模换算      | ✅ `pause`           |
| 12  | **复述不收敛**                         | 布尔            | ✅ `pause`           |

**12 条判据，只有 6 条能停机。** 这 6 条里 4 条是布尔判定（7 的触发、8 的触发、9、10），**真正要调阈值的只有 3 处**：同一错误的次数、连续出界次数、实现期轮次预算。

### 4.5 机制 A：探索期 / 实现期分期

```
explore → implement ：第一次真正改动文件（mutated = true 且非 no-op）
implement → explore ：连续 K 轮无 mutate 且回到纯读取

预算：exploreBudget = f(任务规模) × 3~5   ← 以「读取的文件数」计量
      implementBudget = f(任务规模)        ← 以「轮次」计量
```

**为什么它同时解决两个反向问题**：

- **问题 2（误伤）**：合法的大量读取全落在 explore 的大预算里，**碰不到阈值**
- **问题 1（漏检）**：`implement → explore` 的**回退**是强信号。它判的是**阶段流转**，对「每次读不同文件」免疫

### 4.6 机制 B：读产出判据（解问题 1）

指纹类判据在问题 1 上全失效——它判的是请求重复性，不是信息增益。换两条：

**B1 符号新颖度**（抓「读到的都是已知内容」）

```
knownSymbols ← 符号来源见下（分层：优先复用代码影响面图谱的符号表，未落地时回退正则）
novelty = EMA(新增符号数 / 本轮符号总数, K=5)
连续 5 轮 novelty < 0.1  →  signal: low_symbol_novelty
```

**符号来源分层**（与 `docs/code-impact-graph-plan-2026-09-29.md` 的关系）：

| 层       | 来源                                                                 | 条件                                             | 覆盖                 | 口径                                          |
| -------- | -------------------------------------------------------------------- | ------------------------------------------------ | -------------------- | --------------------------------------------- |
| **首选** | 代码影响面图谱的符号表（`GraphIndex.symbols`，tree-sitter AST 抽取） | 该能力的 L2 已落地，且当前文件在图谱覆盖的语言内 | 多语言，符号边界准确 | 精确                                          |
| **回退** | 从读取结果正则抽函数名 / 类名 / 路径                                 | 上述任一条件不成立                               | 仅文本模式           | 过近似（注释/字符串里的符号会被误算，偏安全） |

**为什么是分层而不是二选一**：判据本身（新颖度 + 连续轮次）与符号来源无关，换源不改判据语义；而 L2 落地前这个判据不能是空的。两层都要，且**回退路径的过近似方向是"多算进度"，不会误伤**——它只会让停滞晚一点被发现，不会把合法探索判成停滞。

**代价**：本模块因此对代码影响面图谱产生一个**软依赖**——L2 未落地时退出回退路径，功能不受影响但覆盖变窄（只有正则能认的模式）；L2 落地后不需要改本模块任何判据，只需把符号来源接过去。

**B2 结构化复述 + 收敛判定（主力）**

超过 `exploreBudget` 时**不是停，是要求一次结构化复述**。必须输出可机械比较的 JSON，不能是自由文本：

```json
{
  "hypothesis": "根因可能在 auth 模块的 token 校验",
  "excluded": ["user.ts", "session.ts"],
  "candidateSet": ["auth/token.ts", "auth/middleware.ts"],
  "nextCheck": { "action": "读 token.ts 的校验分支" },
  "needFiles": ["auth/token.ts"]
}
```

收敛判定：

| 观察                                  | 判定                  |
| ------------------------------------- | --------------------- |
| `candidateSet` 与上次求交后**在收缩** | ✅ 收敛，重置计数     |
| `excluded` 严格增长                   | ✅ 收敛               |
| **候选集换了内容但大小不变**          | ❌ **不收敛——它在猜** |
| 复述无法解析为合法 JSON               | ❌ 不收敛             |

第三条是分水岭：**要判单调收缩性，不是单看集合大小。**

两个细节：**复述本身计入 `exploreBudget`**（否则能被无限触发）；**复述解析失败算不收敛**。

升级路径：复述不收敛 → `reflection`（再给一次）→ 仍不收敛 → `pause`。

### 4.7 机制 C：硬证据类（全为布尔判定）

- **测试数减少即 `pause`** —— Anthropic 原文规则 `It is unacceptable to remove or edit tests`
- **测试回退即 `pause`** —— 「修好 A 弄坏 B」的可检测形式
- **目标漂移** —— 用 `allowedPaths` 出界判定，不是模糊的语义相似度
- **同一错误连续 3 次** —— 确定走不通

### 4.8 状态外置

| 项       | 做法                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| 存哪     | `projectStateRoot(root)/progress/state.json`，落盘策略照搬 `subagent/state-store.ts`（终态立即落盘 + 中间态防抖） |
| 存什么   | 任务级固定部分（`goalFingerprint` / `allowedPaths` / 两套预算）+ 最近 K 轮 `TurnSnapshot` 窗口                    |
| 怎么恢复 | 固定部分**全注入**；窗口部分**只注入 `warn` 及以上**，`info` 留日志——否则又变笨重                                 |
| 生命周期 | 派生数据，落已 gitignore 的状态目录，不进版本控制                                                                 |

### 4.9 终止态与恢复

补充现在缺失的终止态枚举（现在是单一 `pause`）：

```
verified / review-required / blocked / stopped-by-budget
```

- **恢复路径**：`pause` 后人确认 → **从上次快照续跑**，不从头来（复用已有快照 + 会话持久化）
- **三个逃生阀**：① 任务声明放宽阈值；② 模型给出解释后重置计数；③ 用户确认后本任务不再拦
- **探索型任务显式声明**（「调研这个模块」）→ 放宽或关闭机制 B

## 五、关键取舍

| #   | 取舍                           | 选择与代价                                                                                                                                              |
| --- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **判据数量 vs 可停机动数量**   | 12 条里只放 6 条能停。代价是部分真实空转只报警不停；换来的是不误伤合法长任务                                                                            |
| 2   | **低档干预是否改行为**         | `info` / `signal` / `reflection` **只注入上下文，不强制改道**。代价是弱模型可能忽略提示；换来的是不束手束脚。**若现有 `reflection` 会改变行为，需降级** |
| 3   | **只读是否纳入拦截**           | 只读最高到 `info`。代价是纯读取型空转不直接停机；由机制 B 兜底                                                                                          |
| 4   | **探索预算量纲**               | 用「读取的文件数」而不是「轮数」。代价是采集多一个计数；换来的是不把「一轮读 20 个文件」和「一轮读 1 个文件」等同                                       |
| 5   | **收敛判定看大小还是看单调性** | 看单调收缩性。代价是判定复杂一点；换来的是识别「候选集来回换」这种假装收敛                                                                              |
| 6   | **复述是否计入预算**           | 计入。代价是复述本身消耗探索额度；换来的是不能被无限触发                                                                                                |
| 7   | **状态存盘时机**               | 终态立即 + 中间态防抖。代价是崩溃可能丢最多一个防抖窗口；换来的是不每轮同步写盘                                                                         |
| 8   | **是否做独立验证器**           | 本轮不做（列 P2）。代价是验证仍靠确定性证据（测试/编译）而非第二个模型；换来的是不引入第二个模型预算                                                    |

## 六、边界与漏检口径（要能对用户说清）

1. **判据依赖模型能产出结论**——B2 要求结构化复述，弱模型可能说不清。**说不清本身就被判为不收敛**，这不是误伤，是正当升级
2. **符号来源分两层，口径随层而变**（见 §4.6）——首选是代码影响面图谱的符号表（tree-sitter AST，符号边界准确）；回退是正则抽取，此时注释/字符串里出现的符号会被误算（**过近似**）。**过近似对本判据是安全方向**：它只会让停滞晚一点被发现，不会把合法探索误判成停滞。注意这与那个 CodeGraph 项目无关——它用 tree-sitter AST，不做正则抽取
3. **`evidence` 依赖项目本身可跑测试/编译**——没有测试的项目上，机制 C 的三条退化失效，只剩轮次与漂移
4. **`allowedPaths` 由任务初始检索推导，会不准**——因此漂移判据设「连续出界」而非单次，并只作 `reflection` 起步
5. **探索型任务的显式声明是人工口径**，不是自动识别；识别错会放宽本该收紧的判据

## 九、明确不做

| 不做                                          | 理由                                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------------------ |
| 多租户 / 平台级控制面                         | 平台活，与 CLI 形态不匹配                                                            |

| 证据绑定源码版本（`sourceRevision`）          | Proof-of-done 契约里的概念，需要接 git 状态机；本轮先不做                            |
| **语义相似度判停滞**                          | 不可验证、误判率无法量化；业界主流不用。现有 `semantic_stall` 这个名字要么改，要么废 |
| 文件监听 / 后台 daemon                        | 无异步窗口需求，净增复杂度                                                           |
| 用子 agent 做停滞判定                         | 判定要读全局状态，委派出去反而多一次上下文传递                                       |

## 十、风险

| 风险                                              | 影响                                                                  | 处置                                                                                                                                           |
| ------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 机制 B 依赖模型产出结构化合集                     | 弱模型下失效                                                          | 解析失败即判不收敛，退化为「说不清就升级」，仍成立                                                                                             |
| `allowedPaths` 推导不准                           | 漂移误报                                                              | 连续出界才升档；起步只作 `reflection`                                                                                                          |
| 探索预算系数（3~5×）凭经验                        | 系数偏小会误伤、偏大则漏检                                            | 先用评测集测两组系数，取误杀率为 0 的前提下的最小值                                                                                            |
| 状态文件损坏                                      | 判定全部失效                                                          | 照 `store.ts` 的缺失自愈：读不到就重建，不报错                                                                                                 |
| 现有 `reflection` 会改变行为                      | 降级为纯注入后行为变化，可能影响既有评测结果                          | 改造后必须重跑 `eval/suite` 的 11 个用例做对照                                                                                                 |
| 判据数量膨胀                                      | 又变回笨重                                                            | 准入纪律写死在 §4.4：**新增判据默认只能进 `info` / `signal`**，要进门禁需单独论证                                                              |
| **B1 的符号来源对代码影响面图谱有软依赖**（§4.6） | 若把软依赖当硬依赖排期，P3 会被阻塞                                   | **P3 不依赖 L2**：L2 未落地就走正则回退路径，判据照常工作，只是覆盖变窄。**排期上按独立可交付处理**；L2 落地后再把来源接过去，届时不需要改判据 |
| 两条路径的符号口径不同                            | 同一份代码在两条路径下 `novelty` 数值不可比（正则过近似会抬高新颖度） | 阈值 0.1 的标定必须**在所用路径上分别做**；`ProgressSignal.detail` 里带上当前来源，便于事后归因                                                |
