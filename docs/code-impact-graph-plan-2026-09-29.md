# 代码影响面图谱：功能改造规划（2026-09-29）

> 来源：对 CodeGraph（`colbymchenry/codegraph`，MIT，72.3k star）的设计研读与横向对标（含 codemap、code-review-graph、`codegraph-ai/CodeGraph` 三个同类），以及对 `tree-sitter-wasms` **实测的语法覆盖与体积**
> 目的：补上 Oran Code 缺失的「代码结构理解」能力——企业落地场景里优先级最高的一类，且**覆盖主流语言**
> 基线：`main` 分支，**22 个已注册工具 / 首轮暴露 19 / 首轮 Schema 12,557 字节**（2026-09-29 实测）
> 状态：**纯设计文档，未落代码**。初版曾照本文件写过一份 TS-only 草稿，其分支与全部代码已按要求撤销；本文件已改为多语言方案。
> 已定事项：**接受新增 2 个依赖**（`web-tree-sitter` + `tree-sitter-wasms`，见 §11.2）。
> 配套：`docs/progress-detection-plan-2026-09-29.md`（无进展检测改造）。两份互补——本份补「代码结构理解」，那份补「执行过程控制」，共用 `.oran/` 状态目录。**注意两份的抽取机制不同**：本份用 tree-sitter AST，那份用正则抽符号名；若本份的 L2（符号级）先落地，那份的「符号新颖度」可以直接消费本份的符号表，不必自己再抽一遍。
> **方案变更记录**：初版为「自研 TS/JS 单语言 + 正则抽取」，已否决——只懂一种语言的图谱对通用 coding agent 等于不存在（跑别人的仓库十有八九不是 TS，返回空结果比没有这个工具有害）。现方案为 **tree-sitter wasm + 多语言 + 符号级**。

## 一、要解决的问题

### 1.1 主问题

改一个被多处引用的文件之前，agent 回答不了「改这里会波及谁」。它现在只有两条路：

| #   | 现在的做法                        | 失效方式                                       |
| --- | --------------------------------- | ---------------------------------------------- |
| 1   | `search_code` 搜同名文件或字符串  | **覆盖不全**：间接引用（A→B→C 里改 C）搜不出来 |
| 2   | 把候选文件逐个 `read_file` 读一遍 | **工具调用与 token 都爆**                      |

后果两头都错：要么漏改（编译过了但行为坏了），要么过度改动（顺手动了不相干的文件）。

### 1.2 归属：企业侧 P0 场景

一份企业研发 Agent 的落地统计（按角色列高频痛点后收敛成场景）给出的排序是：

| 场景               | 业务价值 | 技术可行性 | 落地成本 | 优先级 |
| ------------------ | -------- | ---------- | -------- | ------ |
| **代码理解与问答** | 高       | 高         | 低       | **P0** |
| 构建失败分析与修复 | 高       | 高         | 低       | **P0** |
| 单测生成与补全     | 高       | 中高       | 中       | **P0** |
| 需求到技术方案初稿 | 中高     | 中         | 中       | P1     |
| 代码评审辅助       | 中       | 中         | 中       | P1     |

它的取舍理由是：**前三个定为 P0，因为「反馈信号最明确、价值最容易量化」**——代码理解可以用「是否准确定位到目标文件」评估；而评审与方案初稿「主观性强、容易扯皮」，放第二阶段。

**本规划落在第一行的 P0 上**，且这是目前唯一完全空白的一块。

### 1.3 三条功能要求（来自使用者，实现必须满足）

| #   | 要求                                                   | 本设计的对应                                                         |
| --- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| 1   | 用户手动触发，为当前项目生成图谱，**保存在当前项目下** | `/graph` 命令；落 `projectStateRoot(root)/graph/`，即 `.oran/graph/` |
| 2   | AI 能读取该图谱                                        | `code_impact` 工具读同一份索引                                       |
| 3   | **即使用户没有手动生成，AI 也能按需调用**              | 索引**懒构建**：工具首次调用时若索引缺失/过期，自动扫描并生成        |

要求 3 是硬要求：**手动生成是「预热」，不是前置条件**。任何「先跑 `/graph` 才能用工具」的设计都不合格。

## 二、对标证据

### 2.1 成熟实现的实测收益（CodeGraph）

7 个真实开源仓库、7 种语言、Claude Code headless、**有图谱 vs 空 MCP 配置**、每组 4 次取中位数，2026-08-05 在 Claude Opus 4.8 上重测：

总口径：**工具调用少 88% · 快 53% · token 少 62% · 便宜 44% · 文件读取全部降到 0。**

| 仓库       | 语言 / 规模    | 工具调用 | 时间    | 文件读取  | token | 成本 |
| ---------- | -------------- | -------- | ------- | --------- | ----- | ---- |
| VS Code    | TS / ~11k 文件 | 2 vs 28  | 2.2× 快 | 0 vs 12   | −77%  | −71% |
| Excalidraw | TS / ~640      | 2 vs 43  | 3.6× 快 | 0 vs 18   | −84%  | −78% |
| Tokio      | Rust / ~790    | 3 vs 29  | 2.6× 快 | 0 vs 19   | −65%  | −64% |
| Django     | Python / ~3k   | 3 vs 14  | 35% 快  | 0 vs 8.5  | −41%  | −13% |
| Alamofire  | Swift / ~110   | 4 vs 33  | 2.6× 快 | 0 vs 16.5 | −59%  | −57% |

它总结的规律：**成本跟「问题需要多少探索」相关，而不是跟仓库大小相关**——在文件阅读式 agent 要 28–43 次工具调用才能回答的问题上降幅 57–78%，在 7 次就够的问题上基本持平。

### 2.2 必须一并记住的反面数据

CodeGraph 主动公开了对自己不利的一项：

> 上面的数字量的是**吞吐**。它没有量上下文窗口里最后剩下什么——**在那一轴向上它是更贵**。同样 7 个仓库的多轮会话，它的响应在会话结束时留下的**常驻检索上下文比文件阅读式 agent 多约 80%**（VS Code 上 67k token 对 18k）。

**更少 token 被处理**和**更大的常驻占用**同时成立，因为高精度换来的是一次性返回一大块逐字源码。

**这一条直接决定我们的输出形态**（见 §4.4 与 §5 第 4 条）：我们只返回**结构**，不返回源码。

### 2.3 一条要照抄的方法学

它的对照组**在两组里都封死了 CLI**：净化过的 `PATH` + 一个 `PreToolUse` hook，拒绝任何对 CLI 的 Bash 调用。原因写在文档里：

> 没有这个封锁，对照组就不是对照组。未封锁时测到 WITHOUT 组的 agent 在 `PATH` 上找到 CLI 并通过 Bash 用了它——**28 次里 26 次**，双向扭曲对比。**更早公布的数字就是没有这个封锁时产出的。**

将来做对照测评时（§8 P4）必须照此办理。

### 2.4 两条体积路线（实测，决定依赖选型）

| 方案                                            | 压缩下载          | 解包                           | 语言数 | 说明                                                    |
| ----------------------------------------------- | ----------------- | ------------------------------ | ------ | ------------------------------------------------------- |
| **CodeGraph**（主包 + 平台原生包 win32-x64）    | 0.4 + **51.7 MB** | 0.4 + **251.5 MB** / 1270 文件 | 20+    | Rust kernel，把语法编译进原生二进制                     |
| **`web-tree-sitter` + `tree-sitter-wasms`**     | 1.1 + **4.3 MB**  | 4.7 + **49.4 MB**              | **36** | 每语言一个 `.wasm`，按需加载                            |
| 同上，改用 `@vscode/tree-sitter-wasm`（精选集） | 1.1 + 2.0 MB      | —                              | 17     | 缺 C / Kotlin / Swift / Scala / Lua / Vue / Dart / ObjC |

**结论：选 `tree-sitter-wasms`。** 多 2.3 MB 下载换来 36 门语法，并补齐 C、Kotlin、Swift、Scala、Lua、Vue、Dart、ObjC。相对 CodeGraph 仍是**下载省 12 倍、磁盘省 5 倍**。

`tree-sitter-wasms@0.1.13` 是预编译 wasm 集合（fork 自 Menci/tree-sitter-wasm-prebuilt，GitHub Actions 自动发布），用法是每语言一个 `.wasm`：`Language.load("<dir>/out/tree-sitter-<lang>.wasm")`。

**关键推论：支持多少语言与体积无关。** 体积由依赖包决定（整包 49.4 MB 固定），我们写多少语言的 resolver 不改变体积。**所以「支持主流语言」的约束是工程量，不是磁盘。**

## 三、抄什么、不抄什么

| #   | 设计点                | CodeGraph 的做法                                                                    | 我们的选择                                                                          | 理由                                                                                                                                                      |
| --- | --------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 工具粒度              | **只暴露一个** `codegraph_explore`，其余工具功能在但默认不上架                      | **只做一个工具** `code_impact`                                                      | 图谱查询是同一次遍历的不同投影；拆成一堆窄工具会让模型去挑，更容易选错                                                                                    |
| 2   | 加载策略              | 配置里 `alwaysLoad: true`，对抗「Claude Code 把 MCP 工具挡在工具搜索后面」          | **不标 `deferred`**，首轮即暴露                                                     | 同一个道理：**一个要被搜出来的图谱工具不会被用到**，模型会退回 grep。这和我们自己踩过的坑一致（首轮延迟 9 个工具 → 核心能力多走一轮 → 回调成只延迟 2 个） |
| 3   | 新鲜度                | 三层：文件监听 + 2s 防抖；**陈旧横幅**；连接时 `(size,mtime)`+内容哈希补齐          | **每次调用同步校验指纹**（不做 watcher）                                            | 同步校验**没有"索引落后于磁盘"的时间窗**，因此不需要 watcher、不需要防抖窗口、也不需要陈旧横幅；代价是每次调用走一遍目录 + stat（解析部分由缓存省下）     |
| 4   | 抽取                  | Rust kernel + tree-sitter 语法编译进原生二进制，20+ 语言                            | **`web-tree-sitter`（wasm 运行时）+ 每语言 tree-sitter query**                      | 同精度、体积小 5–12 倍；代价是解析慢于原生（见 §5 第 6 条）                                                                                               |
| 5   | 输出                  | 一次返回相关符号的**逐字源码**（一个密集 payload）                                  | **只返回文件路径 / 符号列表**，不返回源码                                           | 它的反面数据（常驻 +80%）说明密集 payload 的价格；需要源码时模型再 `read_file`，把"要不要读全文"的决定权留给它                                            |
| 6   | 子 agent              | 明确**反对**把探索委派给读文件的子 agent（否则子 agent 照样读文件，图谱变成纯开销） | 同样**不委派**                                                                      | 直接采纳它的实测结论                                                                                                                                      |
| 7   | 存储                  | 本地 SQLite + FTS5 全文检索                                                         | 单文件 JSON 落 `.oran/graph/`                                                       | 无全文检索需求；单文件 JSON 够用，且与服务端零依赖取向一致                                                                                                |
| 8   | 跨语言桥接 / 框架路由 | Swift↔ObjC、RN 桥、17 个 Web 框架路由、6 个 router 导航边                           | **不做**                                                                            | 属于 CodeGraph 的差异化能力，本轮不追（列入 §9）                                                                                                          |
| 9   | 增量重建              | 只重算变化部分                                                                      | **P0 全量重建，P2 再做增量**                                                        | 见 §5 第 7 条；先保正确，再谈快                                                                                                                           |
| 10  | 语义模型              | SQLite 图 + 符号表                                                                  | **同一套**：节点 = 文件 + 符号，边 = `imports` / `calls` / `extends` / `implements` | 借它验证过的模型，不重新发明                                                                                                                              |

## 四、设计

### 4.1 粒度分层（先文件、后符号）

| 层            | 节点             | 边                                 | 用途                   | 阶段   |
| ------------- | ---------------- | ---------------------------------- | ---------------------- | ------ |
| **L1 文件级** | 文件             | `imports`                          | 「改这个文件会波及谁」 | **P0** |
| **L2 符号级** | 函数 / 类 / 方法 | `calls` / `extends` / `implements` | 「改这个函数谁在调」   | **P2** |

**P0 只做 L1**：它已能回答核心问题，且是 L2 的基础（解析 `calls` 要先有文件级解析器）。**但数据模型一次留够**，避免 P2 改结构。

### 4.2 数据模型

```ts
type LanguageId =
  | "typescript"
  | "tsx"
  | "javascript"
  | "python"
  | "java"
  | "go"
  | "rust"
  | "c"
  | "cpp"
  | "c_sharp"
  | "ruby"
  | "php"
  | "kotlin"
  | "swift"
  | "scala"
  | "lua"
  | "bash"
  | "vue"
  | "dart";

interface GraphIndex {
  version: 1;
  builtAt: string;
  /** 每个文件的语言归属；未识别语言的文件不进图。 */
  languages: Record<string, LanguageId>;
  /** 仓库内源文件，相对路径（正斜杠），已排序。 */
  files: string[];
  /** L1：file -> 它直接引用的仓库内文件（已解析、去重、排序）。 */
  imports: Record<string, string[]>;
  /** L2（P2 起填充）：符号节点与调用边。 */
  symbols?: Array<{ id: string; file: string; kind: SymbolKind; name: string; line: number }>;
  calls?: Array<{ from: string; to: string; provenance: EdgeProvenance }>;
  /** 文件 -> 解析不出来的 specifier（含原因），用于量化漏检而不是静默丢弃。 */
  unresolved: Record<string, Array<{ specifier: string; reason: UnresolvedReason }>>;
}

type SymbolKind = "function" | "class" | "method" | "interface" | "type";
type EdgeProvenance = "resolved" | "heuristic";

type UnresolvedReason =
  | "external" // 裸包名 / 标准库 / 仓库外依赖 —— 设计边界，不是缺口
  | "no-source" // 解析出了路径但仓库里没有对应文件 —— 真缺口
  | "needs-config" // 需要构建配置才能解析（Java source root、C/C++ include 路径…）—— 真缺口
  | "ambiguous" // 解析结果不唯一（C# namespace→file）—— 有损，见 §6 第 3 条
  | "dynamic"; // 运行时才确定（模板拼接、反射、动态 import）—— 设计边界

type LanguageSupport = {
  id: LanguageId;
  extensions: string[];
  /** 对应 tree-sitter-wasms/out/tree-sitter-<grammar>.wasm */
  grammar: string;
  /** 从 AST 抽 import specifier 的 query。 */
  importQuery: string;
  /** specifier -> 仓库内文件路径。这是每语言工作量所在。 */
  resolve: (fromFile: string, specifier: string, ctx: ResolveContext) => ResolveResult;
};

type ResolveContext = {
  fileSet: ReadonlySet<string>;
  /** 构建配置快照，懒解析一次后复用（go.mod / pom.xml / Cargo.toml / tsconfig.json / composer.json…）。 */
  config: ConfigSnapshot;
};
```

**只持久化正向边**，反向索引（谁依赖我）在查询时现算——两份数据落盘就会不同步，现算成本是 O(E)，可接受。

**`unresolved.reason` 是关键字段**（初版只有裸字符串列表）：它把「漏了什么」变成可分类、可统计的，并且**能区分「本该解析却失败」（bug）与「本来就不该解析」（设计边界）**。

### 4.4 工具接口

```
code_impact(path, depth=2, mode="dependents", rebuild=false)
```

| 参数      | 类型                    | 说明                              |
| --------- | ----------------------- | --------------------------------- |
| `path`    | string（必填）          | 要分析的文件，相对 workspace      |
| `depth`   | integer，1–8            | 遍历深度，默认 2                  |
| `mode`    | `dependents` \| `tests` | 全部依赖者 / 只要受影响的测试文件 |
| `rebuild` | boolean                 | 强制全量重建，默认 false          |

权限 `permissionLevel: 0`、`kind: "readonly"`、**`cacheable: false`**（结果反映磁盘当前状态，不能按参数缓存）、`maxOutputChars: 16_000`。

**输出必须恒定带三样交底**（防"静默失效"，见 §6 第 1 条）：索引了多少文件、识别出哪些语言、按 reason 分类的解析失败计数。

### 4.5 新鲜度机制

```
ensureGraph(root, {rebuild}):
  scanned = scanSources(root)              // 走目录 + stat，复用 glob 的忽略规则
  current = fingerprint(scanned)           // sha256(路径 + mtime) 前 16 位
  if 缓存存在 && 缓存.fingerprint === current && 版本匹配:
      return 缓存索引                      // 省掉「读取并解析全部源文件」——最贵的一步
  index = buildGraph(...)                  // 重建（只解析识别出语言的文件）
  缓存写失败不影响本次结果                   // 派生数据，下次重建即可

指纹不匹配 / 缓存缺失 / 缓存损坏 / 显式 rebuild → 全部走重建，不报错。
```

缓存路径：`projectStateRoot(root)/graph/index.json`，即 `.oran/graph/`。

**它是派生数据，落入已 gitignore 的状态目录，不进版本控制**——避免引入「谁来维护、什么时候过期、和代码不同步怎么办」这三个新问题。**「保存在当前的项目下」由 `.oran/` 满足**，但不是把它当项目资产提交。

### 4.6 逐语言解析难度（本方案的工程量所在）

抽取 = 每语言一个 tree-sitter query（**可复制，工作量线性**）。
解析 = specifier → 文件路径（**每语言一套规则，难度天差地别**）。

| 语言                                             | specifier 形态                 | 解析成文件路径需要                                                            | 难度     | 阶段   |
| ------------------------------------------------ | ------------------------------ | ----------------------------------------------------------------------------- | -------- | ------ |
| TypeScript / TSX / JS                            | `./x`                          | 相对路径 + 扩展名补全（`tsconfig` paths 可选）                                | 低       | **P0** |
| Python                                           | `a.b.c` / `.` / `..pkg`        | 包根 + `__init__.py` 规则 + 相对级别                                          | 中       | **P0** |
| Go                                               | `github.com/x/y`               | 读 `go.mod` 的 module path，映射到目录                                        | 中       | **P0** |
| Rust                                             | `crate::foo::bar` / `mod foo;` | 建 crate 模块树（`mod` 声明 + `#[path]`）                                     | 中高     | P1     |
| C / C++                                          | `#include "x.h"`               | 相对 + include 目录（要解析构建配置，且常解析不全）                           | 中高     | P1     |
| Java                                             | `import com.foo.Bar`           | source root + 包目录结构（读 Maven/Gradle 配置）                              | 高       | P1     |
| C#                                               | `using Foo.Bar;`               | namespace → 文件**本质不唯一**（一文件可多 namespace，一 namespace 跨多文件） | **有损** | P2     |
| PHP                                              | `require` / `use`              | 相对路径 + `composer.json` autoload                                           | 中       | P2     |
| Ruby                                             | `require` / `require_relative` | 相对路径 + `$LOAD_PATH` 推断                                                  | 中       | P2     |
| Kotlin / Scala / Swift / Lua / Bash / Vue / Dart | 各自规则                       | 各自规则                                                                      | 中       | P3     |

**P0 只做前三行**：一门相对路径、一门模块点号、一门 module path——**三种解析范式各一**，足以验证管线是否成立。之后每语言是一个独立小板件。

**Java 与 C# 的诚实边界**：它们的组织单位是包/命名空间而不是文件，`import`/`using` 到文件的映射**不唯一**。所以对这两门语言，图谱只能给到「这个命名空间被谁用了」，**给不到文件**；这类边标 `provenance: "heuristic"`，并在 `unresolved` 里记 `ambiguous`。

### 4.7 手动入口：`/graph`

| ----------------------------------- | ----------------------------------------- |
| 文件数 / 边数                       | 按语言分组（`typescript 121 / python 3`） |

## 五、关键取舍

| #   | 取舍                                 | 选择与代价                                                                                                                                       |
| --- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **语言广度 vs 符号深度**             | 先广度（P0–P1 铺 8–10 门到 L1），后深度（P2 做 L2）。代价是"改这个函数谁在调"要等到 P2；换来的是先让功能对**大多数仓库**可用                     |
| 2   | **tree-sitter wasm vs 原生 kernel**  | 选 wasm。代价是解析慢于原生（CodeGraph 用 Rust 并行）；换来下载小 12 倍、磁盘小 5 倍，且不引入平台二进制矩阵                                     |
| 3   | **不标 `deferred`**                  | 首轮暴露数 +1、每会话多付一条 Schema。换来的是模型第一次接触就能用上它                                                                           |
| 4   | **只返回结构、不返回源码**           | 与 CodeGraph 相反。代价是模型可能多一次 `read_file`；换取的是不把常驻上下文推高（对标实测 +80%）                                                 |
| 5   | **不做 watcher，改同步校验**         | 代价是每次调用走一遍目录 + stat；换来的是无时间窗、无 daemon、无防抖参数、无陈旧横幅                                                             |
| 6   | **grammar 惰性加载**                 | 只加载仓库里实际出现的语言。代价是首次遇到新语言有一次加载延迟；换来的是不为不用的语法付运行时内存                                               |
| 7   | **P0 全量重建**                      | 代价是大仓库上改一个文件要重解析全部源文件；换来的是先保正确。增量列为 P2（`imports` 的出边只受该文件影响，是可做的）                            |
| 8   | **缓存放 `.oran/` 而不是提交进 git** | 代价是换台机器要重建一次；换来的是不引入派生数据的同步与维护问题                                                                                 |
| 9   | **Java / C# 只到 namespace 级**      | 代价是这两门语言的影响面不精确；换来的是不假装做到了文件级（诚实标 `ambiguous`）                                                                 |
| 10  | **引入 2 个依赖**                    | 代价是项目从 4 个依赖变 6 个、下载 +5.4 MB、磁盘 +54 MB；换来的是真 AST 与 36 门语言。**这是本方案的前提，不接受则该方案整体不成立**（见 §11.2） |

## 六、边界与漏检口径（要能对用户和模型说清）

1. **零命中必须显式交底（最重要的边界）**
   图谱只识别**注册过的语言**。拿它跑一个未注册语言的仓库，结果是空——**如果此时返回 `(none)` 而不报错，模型会据此判断"改这个文件不影响任何东西"，这比不回答更糟**。
   → 工具返回里必须恒定给出「索引了多少文件 / 识别出哪些语言」；识别语言数为 0 时，返回明确的「本仓库不在图谱覆盖范围内，请改用 `search_code`」，而不是 `(none)`。

2. **解析失败按 reason 分类，不静默丢弃**：`external` 与 `dynamic` 是设计边界；`no-source` / `needs-config` / `ambiguous` 是覆盖缺口——分开统计。

3. **Java / C# 的文件级映射天生有损**（§4.6），这类边标 `provenance: "heuristic"`。

4. **构建配置解析可能不全**：不解析 `go.mod` 的 `replace`、不处理 Maven 多模块继承、不处理 C/C++ 的 generator 表达式——这些计 `needs-config`，不猜。

5. **动态路径解析不出**：模板拼接、反射、`importlib`、`__import__`、条件导入，计 `dynamic`。

6. **不跟踪类型推断**：L2 的 `calls` 只解析能静态确定目标的调用；接口方法调用的实现类确定不了时不猜（或标 `heuristic`）。

7. **`.d.ts` 声明文件不参与建图**（是产物不是源）；自引用不建边。

8. **AST 抽取不误算注释与字符串**——这是相对正则方案的直接收益，也是必须断言的验收项（§7 第 5 条）。

## 七、验收标准

**运行时层**

| #   | 断言                                               |
| --- | -------------------------------------------------- |
| 1   | `Parser.init()` 只调用一次；并发调用不重复初始化   |
| 2   | 同一 grammar 只加载一次；多次解析复用同一个 parser |
| 3   | 未注册语言的文件不进图，且不导致异常               |

**抽取层（每支持一门语言就加一组）**

| #   | 断言                                                                                             |
| --- | ------------------------------------------------------------------------------------------------ |
| 4   | TS：静态 `import` / `export ... from` / 动态 `import()` / `require()` / 纯副作用 import 全部抽到 |
| 5   | TS：**注释与字符串里的 `from "x"` 不被抽到**（相对正则方案的直接收益，必须断言）                 |
| 6   | Python：`import a.b.c` / `from . import x` / `from ..pkg import y` 抽到，且相对级别正确          |
| 7   | Go：module path 形式的 import 抽到，并按 `go.mod` 映射到目录                                     |
| 8   | 同一 specifier 重复出现只产生一条边                                                              |

**解析层**

| #   | 断言                                                                                           |
| --- | ---------------------------------------------------------------------------------------------- |
| 9   | TS：`./a` → `a.ts`、`./a.ts` 精确、`./nested` → `nested/index.ts`、`./legacy.js` → `legacy.ts` |
| 10  | Python：`a.b.c` → `a/b/c.py` 或 `a/b/c/__init__.py`                                            |
| 11  | Go：`<module>/internal/x` → `internal/x/` 下的文件                                             |
| 12  | 解析失败的 specifier 进 `unresolved` 且 `reason` 分类正确                                      |
| 13  | 仓库外/标准库引用记为 `external`，不计入覆盖缺口                                               |

**查询层**

| #   | 断言                                                                        |
| --- | --------------------------------------------------------------------------- |
| 14  | 依赖者 BFS 层级正确：深度 1 = 直接、深度 n = 逐层                           |
| 15  | **环形依赖不导致无限展开**（visited 集合生效）                              |
| 16  | 环检测能报出参与环的文件                                                    |
| 17  | `mode=tests` 只返回测试文件，且能**跨语言**（如 TS 改动的测试在 Python 里） |

**缓存层**

| #   | 断言                                                                    |
| --- | ----------------------------------------------------------------------- |
| 18  | 首次调用 `cached: false`，第二次 `cached: true`                         |
| 19  | **改动任一被索引文件的 mtime 后，下一次调用必须重建**                   |
| 20  | **删掉缓存后调用能自动重建，不报错**                                    |
| 21  | **用户从未手动生成过图谱时，工具首次调用即可返回结果**（要求 3 的验收） |

**工具层**

| #   | 断言                                                        |
| --- | ----------------------------------------------------------- |
| 22  | `code_impact` 已注册且 `isExposed()` 为真（未标 deferred）  |
| 23  | 传入未被索引的路径 → 返回可读错误，不抛异常                 |
| 24  | **识别语言数为 0 的仓库 → 返回"不在覆盖范围"而非 `(none)`** |
| 25  | 输出恒定包含「索引文件数 / 语言分布 / unresolved 分类计数」 |

**对照测评（P4）**：同一批问题在有 / 无图谱两组各跑 4 次取中位数，**两组都封死图谱入口**（§2.3），并同时报告吞吐与常驻上下文两个轴。

## 九、明确不做

| 不做                                                     | 理由                                                     |
| -------------------------------------------------------- | -------------------------------------------------------- |
| 文件监听 / 后台 daemon                                   | 同步校验已消除时间窗，再加 watcher 是净增复杂度          |
| Rust 原生 kernel / 平台二进制矩阵                        | 体积换性能不划算（下载 12 倍、磁盘 5 倍）；wasm 精度相同 |
| 跨语言桥（Swift↔ObjC、RN、Expo）                         | CodeGraph 的差异化能力，与我们的用户群不匹配             |
| 17 个 Web 框架的路由节点 / router 导航边                 | 同上；同精度要逐框架写解析                               |
| 返回逐字源码                                             | 会把常驻上下文推高约 80%，与已有截断机制冲突             |
| 拆成一堆窄工具（`callers`/`callees`/`imports`/`files`…） | 单工具是对标收敛的结论，也省每次会话的 Schema            |
| 把图谱提交进 git                                         | 派生数据；提交会引入同步与维护成本                       |
| 可视化（依赖图 / HTML / 交互面板）                       | 与本仓库技术取向无关，成本高、收益只在人看               |
| 语义相似度之类"猜"的解析                                 | 不可验证；解析不出就记 `unresolved`，不猜                |
| 全文检索（FTS5 对位）                                    | 已有 `search_code`；先不做第二套检索                     |

| ---------------- | ---------------------------------------------------- |
| 已注册工具       | **22**                                               |

加入 `code_impact` 后的预期：注册 23 / 首轮暴露 20 / Schema 约 13.0–13.3 KB（**待实测**）。

> ⚠️ 注意：**「18 个内置工具、首轮暴露 16、Schema 10,660 字节 ≈ 10.4 KB」这组数字已经过期**——那是工具数还是 18 时的口径，现在实际是 22 / 19 / 12,557。任何引用了旧数字的地方（项目说明、简历、面试准备材料）都需要按实测值更正，**更正前先跑一次注册表序列化，不要照抄本文档的估值**。

复现命令：

```bash
node -e "import('./packages/oran-code/dist/tools.js').then(m=>{const r=new m.ToolRegistry();
m.registerBuiltinTools(r,process.cwd());
console.log('registered', r.list().length);
console.log('exposed', r.listExposed().length);
console.log('bytes', Buffer.byteLength(JSON.stringify(r.schemas())));})"
```

口径纪律不变：这个数字是**首轮下发工具 Schema 的静态 JSON 字节体积**，不是 token 账单、不是延迟、不是性能提升。

### 11.2 新增运行时依赖（P0 之前必须决定）

本方案引入两个依赖，将是项目至今第 5、第 6 个（现有：`@modelcontextprotocol/client`、`ink`、`react`、`yaml`）：

| 包                  | 版本   | 压缩下载 | 解包    | 用途                  |
| ------------------- | ------ | -------- | ------- | --------------------- |
| `web-tree-sitter`   | 0.27.0 | 1.1 MB   | 4.7 MB  | wasm 解析运行时       |
| `tree-sitter-wasms` | 0.1.13 | 4.3 MB   | 49.4 MB | 36 门语言的预编译语法 |

**2026-09-29 已实测可安装**（`pnpm add`，42.6s；无 postinstall、主包零 JS 依赖），验证后已回滚，未留在 `package.json` / `pnpm-lock.yaml`。

**决定（2026-09-29）：接受这两个依赖。** 项目此前刻意保持 4 个依赖，现变为 6 个，代价是下载 +5.4 MB、磁盘 +54 MB；换来的真 AST 与 36 门语言是本方案的前提。**若不接受，则本规划整体不成立**——只能回到「正则 + 单语言」，而那已被否决。

依赖落地的具体动作留给 P0 第一步：`pnpm add web-tree-sitter tree-sitter-wasms`（在 `packages/oran-code/` 下），装完先跑 P-1 的三个验证项。
